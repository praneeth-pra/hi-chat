# Accuracy mode and question extraction

Accuracy now holds the draft until review completes. The two 120B models still race to prepare the draft; Groq 20B remains a draft recovery option. A 120B reviewer prefers the other provider, checks the complete draft against the original conversation and Exa web evidence, and either approves it, replaces it, or gives an answer that states material uncertainty. Groq and Cerebras currently serve the same underlying gpt-oss-120b model: separate passes and sources improve checking but do not establish frontier-level quality or guarantee correctness.

Web search is required in Accuracy. Set `EXA_API_KEY` securely in the Railway service's variables and deploy/restart the service after saving it. The key stays in the Node relay. Browser calls use authenticated, same-origin `/api/search`; nginx enforces login, a request-size limit and a rate limit. The relay calls only Exa's fixed HTTPS search endpoint and returns at most five excerpts and source URLs. It does not execute instructions in sources or fetch arbitrary submitted URLs. Search text is not logged. The current question and up to two preceding user prompts provide search context (at most 4,000 characters total); assistant answers, keys and attachment payloads are excluded.

Search uses Exa Fast (`type: 'fast'`) and overlaps drafting with a 4.5-second server timeout and a 6-second browser deadline. No usable evidence means no Accuracy answer: the UI reports the problem and offers retry or Speed mode. Excerpts are evidence, not proof; reviewers are instructed to reject irrelevant/outdated sources and unsupported certainty. Source links are shown with each reviewed answer. No real Exa/provider request was made from this workspace; automated tests use stubbed upstream responses. Production key validity and provider accuracy still need a live check after deployment.

Review responses must pass JSON validation. Review has a 15-second total deadline, with at most 10 seconds for the first provider. A failed or incomplete review can recover using the other 120B provider; if neither succeeds, the app reports an error without showing the unchecked draft. Stop cancels review/search. Normal MCP tool calls retain the existing approval path, and their eventual answer is reviewed. The reviewer itself receives no executable tools. Speed mode and manually selected models keep their normal streaming paths. Accuracy deliberately trades time to first visible answer for checking; metadata records drafting and review durations, reviewer, verdict and sources. Longer answers naturally take longer to finish.

Use the list icon in a chat header to extract questions. Extraction runs only after clicking **Extract questions**, snapshots that chat's user text, and excludes assistant/tool messages and attachment metadata/content. A 120B judge extracts exact source spans, including scenario questions and follow-ups. Unknown prompt indices, altered wording and incomplete responses are rejected; Groq is the fallback for Cerebras. Large chats are processed in bounded batches without dropping older prompts. Very long single prompts are split across batches, so questions spanning a batch boundary may need review. The result preserves prompt order, keeps repeated questions from different prompts, and can be copied without adding messages to the chat. Cancel, closing the dialog or changing chats aborts extraction; a failed batch never produces a misleading partial list.

The trash icon in the chat header or beside a sidebar chat opens the existing confirmation dialog. Confirming deletion stops that chat's generation. Deleting another chat keeps the active page; deleting the active chat returns home. Native button activation handles Enter once.

The updated Hammerspoon helper uses physical **fn + Right Arrow** to send the prompt (including macOS End-key translation). Plain arrows, fn + Left and fn + Return are released. Missing-Jan-window messages and typing ON/OFF messages use the console instead of popups. Copy `scripts/hammerspoon/jan-remote.lua` into `~/.hammerspoon/init.lua` and reload on the Mac; deploying the web app does not update a local script. Linux checks validate callback behavior, not actual macOS key events.
