# Accuracy mode and question extraction

Accuracy retrieves Exa Fast evidence before drafting. No model request starts without usable sources. The two 120B models receive the same numbered excerpts and race to prepare a grounded draft; Groq 20B remains a draft recovery option and receives that evidence too. A 120B reviewer prefers the other provider, checks the complete draft against the original conversation and excerpts, and either approves it, replaces it, or gives an answer that states material uncertainty. A completed detailed audit is preferred; incomplete recovery is explicitly labelled when necessary to keep a response available. Groq and Cerebras currently serve the same underlying gpt-oss-120b model: separate passes and sources improve checking but do not establish frontier-level quality or guarantee correctness.

**Personal questions skip search.** Introductions, past projects, behavioural "tell me about a time" questions and HR logistics (notice period, why you're leaving) are detected by `isPersonalQuestion` and answered from the assistant instructions and documents instead; the review checks them against that background. Every other question needs web search.

**Reviewers.** With a Claude provider set up (Model Providers, Anthropic or a custom provider at api.anthropic.com), every reviewer (Claude Sonnet 5.5, Cerebras and Groq gpt-oss-120b) runs the detailed claim audit at the same time. Claude's verdict wins if it is valid within 2.5 seconds of the review starting (`CLAUDE_WINDOW_MS`); after that the first valid gpt-oss audit is shown and the rest are cancelled. Cerebras (or the only configured provider) writes one recovery answer at the same time as the audits; it is shown, labelled unverified, only once every gpt-oss audit has failed and Claude has failed or missed its window, so a failed audit no longer adds a second round trip. The log line's `reviewers=` field lists each reviewer's time and outcome. Claim support of type "context" may quote the user's messages or the assistant instructions/documents (the resume), never earlier assistant answers.

**Logs.** Each Accuracy answer posts one line to Railway through `/api/speech-log`: `accuracy: verdict=… model=… search=ready|skipped sources=N total=…ms search_time=…ms draft=…ms review=…ms claims=N context_claims=N unsupported=N fallback=… failures=provider:reason,…`. No question, answer or source text is logged.

Web search is required in Accuracy for all other questions. Set `EXA_API_KEY` securely in the Railway service's variables and deploy/restart the service after saving it. The key stays in the Node relay. Browser calls use authenticated, same-origin `/api/search`; nginx enforces login, a request-size limit and a rate limit. The relay calls only Exa's fixed HTTPS search endpoint and returns at most five excerpts and source URLs. It does not execute instructions in sources or fetch arbitrary submitted URLs. Search text is not logged. The current question and up to two preceding user prompts provide search context (at most 4,000 characters total); assistant answers, keys and attachment payloads are excluded.

Search uses Exa Fast (`type: 'fast'`) with a 4.5-second server timeout and a 6-second browser deadline. The query asks for authoritative primary sources, preferably official documentation; this is a ranking preference, not an official-domain filter or an authority guarantee. Search completes before drafting, then review follows the full draft. Sources are reused across tool steps within the same user send. No usable evidence means no Accuracy draft or answer: the UI reports the problem and offers retry or Speed mode. Excerpts are evidence, not proof; both passes distinguish standard features from custom libraries and qualify unknown library/version behavior. A missing name in a partial excerpt is not proof that the feature does not exist. Source links use the same numbering supplied to the models. No real Exa/provider request was made from this workspace; automated tests use stubbed upstream responses. Production key validity and provider accuracy still need a live check after deployment.

Review responses require a verdict, a nonempty bounded claim audit, and an unsupported-claim list. Each source-backed claim must match the final answer’s visible wording (backticks and bold formatting may differ; code identifiers/operators are preserved) with a valid source ID and a supporting excerpt. Plain prose spans may differ in case, quote marks, dashes, Markdown and `[n]` citation markers, and spans of ten or more words may differ by one word in ten (`nearSpan`); spans with code characters, words containing digits, and spans under six words must match exactly. User-context claims must quote a user message, not an earlier assistant answer. Explicit uncertainty, clarifying questions and proposed approaches can be marked qualified without inventing supporting citations. Approval cannot coexist with reported unsupported claims; a revision cannot silently retain a reported unsupported assertion without qualification. Missing audits, nonexistent sources, fabricated quotes, malformed JSON and truncated review responses are rejected. Code validates references and spans; relevance, authority, whether a quote actually entails a claim, whether every material claim was audited, and whether a qualification is meaningful still depend on model judgment.

Review has a 15-second total deadline, with at most 10 seconds for the first provider. The first provider performs the detailed claim audit using schema-constrained JSON. If that audit fails, the other 120B provider checks the sources and produces a complete corrected answer using a smaller schema. Recovery answers are labelled “Revised answer · Detailed evidence check unavailable”; they do not count as having passed the detailed audit. If neither provider can produce a usable correction, the already source-grounded draft is returned with “Review unavailable · Answer not fully verified”. This is an availability fallback, not a correctness guarantee. Stop never triggers a fallback answer. An endpoint that answers a schema request with 400 or 422 (Groq does not always name the schema in its error) retries in JSON mode within the same attempt deadline; reference validation still applies to the detailed audit. Only safe failure categories and durations are logged; provider bodies and credentials are not echoed. Stop cancels review/search. Normal MCP tool calls retain the existing approval path, and their eventual answer is reviewed. The reviewer itself receives no executable tools. Speed mode and manually selected models keep their normal streaming paths. Metadata records search time, full draft time (including readiness), review time, claim counts, reviewer, verdict and source links; full claim text and supporting quotes are not persisted in review metadata or timing logs. Accuracy now waits for search before generation and claim audits add review output, so time to first visible answer can increase. No latency improvement or hallucination-rate reduction has been measured in this workspace.

Use the list icon in a chat header to extract questions. Extraction runs only after clicking **Extract questions**, snapshots that chat's user text, and excludes assistant/tool messages and attachment metadata/content. A 120B judge extracts exact source spans, including scenario questions and follow-ups. Unknown prompt indices, altered wording and incomplete responses are rejected; Groq is the fallback for Cerebras. Large chats are processed in bounded batches without dropping older prompts. Very long single prompts are split across batches, so questions spanning a batch boundary may need review. The result preserves prompt order, keeps repeated questions from different prompts, and can be copied without adding messages to the chat. Cancel, closing the dialog or changing chats aborts extraction; a failed batch never produces a misleading partial list.

The sidebar trash icon and sidebar menu's Delete action delete immediately. The chat header and project page retain confirmation. Deletion stops that chat's generation. Deleting another chat keeps the active page; deleting the active chat returns home. Native button activation handles Enter once. Header action buttons sit above the window-drag layer so pointer clicks reach them.

The updated Hammerspoon helper uses physical **fn + Right Arrow** to send the prompt (including macOS End-key translation). Plain arrows, fn + Left and fn + Return are released. Missing-Jan-window messages and typing ON/OFF messages use the console instead of popups. Copy `scripts/hammerspoon/jan-remote.lua` into `~/.hammerspoon/init.lua` and reload on the Mac; deploying the web app does not update a local script. Linux checks validate callback behavior, not actual macOS key events.
